## 一、更新分三級

- **R-UPD-001**：新版上線後使用者怎麼換到新版，只有三級，不得自創第四種：
  - **L0 一般更新**（預設）：不打斷使用者。
  - **L1 強制更新**：`public/runtime-config.json` 的 `minBuild`。
  - **L2 停用離線快取**：同檔的 `swEnabled: false`。
- **R-UPD-002**：每個上線批次的 evidence 必答一行「強制更新：否」或「強制更新：是（R-UPD-010 第 N 項）」。沒寫視為驗收未完成。
- **R-UPD-003**：L1、L2 是「改正式設定」，由顧問三行裁定（決定／理由／風險與回退）後 PM 執行；不走前端直推流程。例外只有 R-UPD-022。

## 二、L1 強制更新：何時觸發

- **R-UPD-010**：符合任一項才用 L1：
  1. 舊版前端會寫出錯誤資料或違反資料契約。
  2. 安全或權限修補。
  3. 後端已部署不相容變更（Functions 參數或回傳、Rules 收緊），舊版核心流程必定失敗。
  4. 核心流程壞掉的修正：登入、報名、取消、候補、簽到、建立或編輯活動。只限「流程走不完或會寫錯資料」；這些頁面上的文案、樣式修正不算（照 R-UPD-011）。
  5. 費用、名額、候補順位，或活動時間、地點、取消狀態顯示錯誤（會讓人白跑或付錯錢的顯示）。
- **R-UPD-011**：以下一律不用 L1：文案、樣式、新功能、效能改善、後台專用頁、非核心頁的顯示問題。理由：L1 會讓所有開著的頁面重新載入，打斷使用中的人。**R-UPD-010 優先於本條**：後台頁若會寫出錯誤資料，仍屬 R-UPD-010 第 1 項。
- **R-UPD-017**：L1 管不到「舊版壞到主程式跑不起來」的情況（主程式沒跑就讀不到 `minBuild`）。白畫面、開不了頁不是 L1 的適用情境，照第四節處理。
- **R-UPD-018**：L1 的實際效力（UPD-1b 已補上）：所有瀏覽器都檢查 `minBuild`，不依賴離線快取支援，`swEnabled: false`（L2 停用期間）也照查；頁面載入後檢查一次，之後回到前景或從上一頁快取還原（`pageshow`）時重讀設定（間隔至少 10 分鐘）；換頁、關閉彈窗、恢復連線只重新評估已延後的強制更新，不重讀設定。開著不關而一直停在前景的分頁，最多要等到下一次回前景才會看到新值，包含 `minBuild` 改回 0 時收掉強制提示框也是。需要立即止血時仍不得只靠 L1，後端要同時擋（Functions／Rules 拒絕舊版請求）或照 R-UPD-016 安排順序。
- **R-UPD-012**：拿不準是否符合 R-UPD-010 時不用 L1，改問顧問。

## 三、L1 怎麼做

- **R-UPD-013**：步驟（照順序，不得跳）：
  1. 修正已通過該批的審查與驗收。
  2. 把 `minBuild` 改成**下 commit 當下的台北時間** `YYYYMMDDHHmm`（12 位數字）。這個值必須**大於線上有問題那一版的建置編號**（同一分鐘內打包的舊版不會被強制，遇到就等下一分鐘再下 commit）。UPD-1 上線後改用 `npm run force-update`，不手打；腳本會讀線上 `/version.json` 比對，值不大於線上建置編號就失敗。
  3. `minBuild` 可以和修正同一批推送（建議，兩者一起生效或一起失敗），也可以在修正上線後單獨推送。單獨推送照樣跑 `npm run bump-version`。
  4. 推送後讀回 `https://toosterx.com/runtime-config.json`，確認 `minBuild` 是剛寫的值。
  5. 確認線上新版的建置編號 ≥ `minBuild`：讀 `https://toosterx.com/version.json` 直接比數字（UPD-1 起有此檔；頁面自己判斷版本只讀自己那份 `index.html` 的 meta，見 R-UPD-033）。不符就立刻照 R-UPD-015 回退。
  6. 用一個部署前就開著的舊分頁確認會換到新版：切到背景超過 10 分鐘再切回來，頁面自己換版（畫面不安全時延後，變安全時自動再試）。
  7. 把值、時間、兩項確認結果記入 evidence。
- **R-UPD-014**：硬條件：`minBuild` 不得大於「含這個值的那次部署」的建置編號。建置編號是打包當下的台北時間，所以值只能是現在或過去，**不得填未來時間、不得多打或少打位數**；測試必須擋下大於執行當下時間的值。若部署平台設了 `FCB_BUILD_ID` 環境變數，建置編號不再是時間，L1 停用並回報顧問；UPD-1 起由打包程式硬擋（Cloudflare Pages 建置環境出現 `FCB_BUILD_ID` 就讓建置失敗），不只靠本條文字。`runtime-config.json` 的格式由測試強制：`swEnabled` 只能是布林、`minBuild` 只能是 0 或 12 位整數（字串 `"false"` 會被當成開啟）。
- **R-UPD-015**：回退：把 `minBuild` 改回上一個值（沒有就 `0`）再推一次。`minBuild` 只升不降是常態；降回只用在填錯。
- **R-UPD-016**：後端不相容變更（R-UPD-010 第 3 項）的順序固定為：新前端先上線 → L1 生效並讀回 → 才部署後端。後端先上是違規。讀回設定檔只證明檔案在線上，不證明舊分頁已換版：L1 讀回後至少再等 30 分鐘才部署後端，而且後端對舊版請求要回明確的錯誤（不得照舊格式寫入）。

## 四、L2 停用離線快取

- **R-UPD-020**：只在離線快取本身出問題時用：白畫面、卡在舊版換不掉、新版安裝一直失敗、L1 推了仍有人停在舊版。效果是所有人改走網路、較慢但一定拿到最新版。
- **R-UPD-021**：做法：`swEnabled` 改 `false` 推送 → 讀回線上檔 → 找到原因修好並在 staging 驗證後才改回 `true`。改回 `true` 同樣要顧問裁定。
- **R-UPD-022**：正式站白畫面且 15 分鐘內聯絡不到顧問時，PM 可以先做 L2 再補報（顧問 2026-11-10 預先裁定：L2 只會讓網站變慢，不會壞資料，回退是改回 `true`）。L1 沒有這個例外。**先分辨是哪一種白畫面**：無痕視窗（沒有離線快取）開正式站正常，才是離線快取問題，用 L2；無痕視窗也白畫面是壞部署，L2 沒有用，改 `git revert` 該批推回上一版（屬緊急修正，照前端推送流程、事後補報顧問）。
- **R-UPD-023**：L2 現況的限制（UPD-3 保險上線前）：`swEnabled` 由主程式讀取，主程式跑不起來的人收不到 L2。這種情況唯一的路是 `git revert` 推回好的版本，讓導覽（網路優先）拿到好的 HTML。

## 五、不得弄壞救援路徑

- **R-UPD-030**：後端變更一律先相容上一版前端；相容做不到才用 R-UPD-016。理由：L0 之下舊版前端可能留在使用者手機上很多天。
- **R-UPD-031**：`/runtime-config.json` 與 `/version.json`（UPD-1 新增）必須維持不快取（`no-store`）且不進離線快取清單；`/sw.js` 維持 `no-cache`；App 的 HTML 不得被瀏覽器或 CDN 快取住（現況靠 Cloudflare Pages 預設的 `max-age=0, must-revalidate`，2026-11-10 實查；不得加會蓋掉它的規則）。改 `_headers` 或 `globIgnores` 時逐項確認，並由測試檢查產出的 `_headers`。
- **R-UPD-032**：`minBuild` 與重新載入的保護不得拿掉：每個 `minBuild` 值每個分頁的自動重新載入有次數上限（UPD-1b 起最多 2 次、間隔至少 60 秒，且**真的執行重新載入時才記一次**；跨分頁另有煞車：同一個 `minBuild` 值累計自動重整 6 次後只顯示按鈕、換值才重算，不會自行恢復；`localStorage` 或 `sessionStorage` 不能讀寫時也只顯示按鈕）；送出中（`data-submitting`）不重新載入；彈窗開著或表單編輯中改跳提示。重新載入後仍是舊版（建置編號仍小於 `minBuild`）時，第 2 次要先清掉離線快取再從網路載入。因畫面不安全而延後的強制更新，畫面變安全時（換頁、彈窗關閉、回到前景）要自動再試，不得只等使用者按。
- **R-UPD-033**：版號（`APP_VERSION`）、建置編號（`VITE_BUILD_ID`）、commit 編號（`VITE_BUILD_SHA`）這類「每次部署都變」的值，不得出現在會被長快取的 JS 檔內容裡，只能放在 `index.html` 與 `/version.json`。**頁面判斷「自己是第幾版」只能讀自己那份 `index.html` 裡的值**；`/version.json` 永遠是線上最新版，只給人與腳本讀回用，程式拿它當自己的版本會讓舊版以為自己已經是新版、強制更新不動作。同一份原始碼換版號、換建置時間重新打包，`assets/` 的檔名必須完全不變（UPD-1 上線後由測試強制；上線前新增程式碼不得再擴大匯入 `src/version.ts` 的範圍）。
- **R-UPD-034**：本機快照（`localStorage` 的 `fcb:*` 快照）只認資料格式版本 `v`，不認版號。改了快照欄位或語意必須加 `v`，舊快照自動作廢。快照不得用來顯示活動狀態、名額、報名狀態這類會過期的判斷。

## 六、UPD-3（背景下載＋更新提示）上線後才生效

> 這一節在 UPD-3 上線前不適用；上線那一批把本行改成「已生效（版號）」。

- **R-UPD-035**：L0 的行為固定為：開頁用本機已存的版本 → 新版在背景下載完成後才跳提示 →「現在更新」立即換版並重新載入一次 →「稍後」本次不再提示、下次重新開啟自動是新版 → 新版下載完成超過 24 小時，頁面回到前景且畫面安全時自動套用。
- **R-UPD-036**：救援不得依賴主程式能執行：離線快取程式自己要讀 `runtime-config.json`；`index.html` 要有獨立的開機檢查（主程式逾時未掛載就換新版或清掉離線快取後從網路重載，每個分頁一次）。這兩項任一失效不得上線。
- **R-UPD-037**：L1 在這個模式下的流程：向伺服器要新版 → 安裝完成 → 切換 → 重新載入；20 秒內辦不到就清掉離線快取從網路重載。提示框不提供「稍後」。
- **R-UPD-038**：頁面回到前景時重讀 `runtime-config.json`（間隔至少 10 分鐘），不只在載入時讀。（已由 UPD-1b 實作並生效，不必等 UPD-3。）
- **R-UPD-039**：離線快取只接管 App 頁面；`/blog`、`/seo`、`/roles`、`/inventory`、`/privacy`、`/terms`（含 `.html` 寫法）、`manual.html` 等內容頁，以及 `_worker.js` 處理的分享預覽網址（`/event-share`、`/team-share`）不得被換成 App 外殼。名單至少涵蓋 `vite.config.ts` `globIgnores` 裡的內容頁與 `_routes.json` 列的路徑，由測試比對。（現況：導覽規則接管所有網址，內容頁在網路超過 3 秒且沒有暫存時會被換成 App 外殼，屬既有問題，UPD-3a 修。）
- **R-UPD-043**：多個分頁與久未關閉的分頁：「下次開啟自動是新版」不得依賴所有分頁都關閉——開機階段發現有等待中的新版就先切換再載入；其他分頁收到切換通知時照安全重載判斷處理（不安全就跳提示）。從上一頁快取或凍結狀態回來（`pageshow` 的 `persisted`、`visibilitychange`）要重跑版本檢查。按過「稍後」要記在該分頁，同一版不再跳。
- **R-UPD-044**：背景下載失敗不得讓使用者卡住也不得無限重試：新版安裝失敗或逾時就維持舊版、不跳提示、下次開頁再試；連續失敗要有可觀察的紀錄（至少 console 與既有的錯誤回報管道）。
- **R-UPD-045**：8 秒開機檢查不得誤殺慢網路：判斷依據是「主程式有沒有開始執行」而不是「畫面有沒有畫完」；主程式已開始執行但之後某一頁壞掉，由既有的錯誤邊界與 `chunk-reload.ts` 處理，不走開機檢查。
- **R-UPD-046**：離線快取程式的自我檢查要用真的打包產物在 staging 驗證（`generateSW` 產出的檔不能直接讀 JSON，做法由 Opus 設計時定：外掛一支自訂腳本，或改用 `injectManifest`），不得只靠單元測試的替身。自訂腳本要自帶「這份離線快取程式的建置編號」（打包時寫入、檔名帶編號），不得向 `/version.json` 問自己的版本。
- **R-UPD-047**：救援先行、分兩次上線：開機檢查、離線快取程式自讀設定、內容頁排除（R-UPD-036、039、045、046）先以「行為仍是網路優先」的一版上線並在 staging 做完壞版演練（UPD-3a）；下一版才改成「先用本機版本、背景下載、跳提示」（UPD-3b）。理由：救援若和行為切換同一版上線，救不了那一版自己。兩版都照 R-UPD-041。
- **R-UPD-048**：「送出中不重新載入」必須真的有人標記：報名、取消、簽到與出席存檔、建立與編輯活動這些寫入進行中（含延遲送出的等待時間）要設上 `data-submitting`，或由安全重載判斷直接讀這些流程的進行中狀態。UPD-1b 已補上（`src/core/submit-guard.ts` 的 `beginSubmitting`／`withSubmitting`，接在資料層與共用 hook，預設每筆最多保留 90 秒自動解除並警告，出席結算放寬到 5 分鐘），並有各流程的測試；新增寫入流程時要同步接線。
- **R-UPD-041**：動到更新流程（`vite.config.ts` 的 workbox 設定與分塊設定（`manualChunks` 或 `codeSplitting`）、`sw-control.ts`、`reload-safety.ts`、`chunk-reload.ts`）的卡一律高風險（含 UPD-1b、UPD-2；只改分塊的卡可免壞版演練，但 staging 要把每一頁走過一次）：Opus 設計與終審、staging 先跑至少一天、做一次「壞版救得回來」演練、單獨上線不夾其他卡、上正式前把 staging 證據送顧問。

## 七、上線節奏

- **R-UPD-040**：已退休（站長 2026-11-11 親口要求刪除「每天最多兩批」限制，取代顧問 §3.84 原條文；編號不重用，R-GOV-010）。上線批次數量沒有上限，節奏由 R-UPD-041 與各批的審查、驗收決定。
- **R-UPD-042**：上線批次的做後量測要包含「改版後第一次開」：先用上一版開過頁，部署新版後再開同一頁，記 JS 請求數、下載量、內容出現時間。
