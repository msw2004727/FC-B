# 改版更新與強制更新規則（R-UPD）

> 2026-11-10 站長指示新增（顧問定稿）。取代原本「強制更新只存在於程式註解、沒有成文規則」的狀態。
> 計畫與證據：FC repo local-only `docs/specs/lite-convergence/update-flow-plan-2026-11-10.md`。
> 取捨順序照 FC `CLAUDE.md` R-CTX-008：穩定 → 速度 → 省錢。

## 一、更新分三級

- **R-UPD-001**：新版上線後使用者怎麼換到新版，只有三級，不得自創第四種：
  - **L0 一般更新**（預設）：不打斷使用者。
  - **L1 強制更新**：`public/runtime-config.json` 的 `minBuild`。
  - **L2 停用離線快取**：同檔的 `swEnabled: false`。
- **R-UPD-002**：每個上線批次的 evidence 必答一行「強制更新：否」或「強制更新：是（R-UPD-010 第 N 項）」。沒寫視為驗收未完成。
- **R-UPD-003**：L1、L2 是「改正式設定」，由顧問三行裁定（決定／理由／風險與回退）後 PM 執行；不走前端直推流程。例外只有 R-UPD-022。

## 二、L1 強制更新：何時觸發

- **R-UPD-010**：符合任一項才用 L1：
  1. 舊版前端會寫出錯誤資料或違反資料契約。
  2. 安全或權限修補。
  3. 後端已部署不相容變更（Functions 參數或回傳、Rules 收緊），舊版核心流程必定失敗。
  4. 核心流程壞掉的修正：登入、報名、取消、候補、簽到、建立或編輯活動。
  5. 費用、名額、候補順位顯示錯誤。
- **R-UPD-011**：以下一律不用 L1：文案、樣式、新功能、效能改善、後台專用頁、非核心頁的顯示問題。理由：L1 會讓所有開著的頁面重新載入，打斷使用中的人。
- **R-UPD-012**：拿不準是否符合 R-UPD-010 時不用 L1，改問顧問。

## 三、L1 怎麼做

- **R-UPD-013**：步驟（照順序，不得跳）：
  1. 修正已通過該批的審查與驗收。
  2. 把 `minBuild` 改成**下 commit 當下的台北時間** `YYYYMMDDHHmm`（12 位數字）。UPD-1 上線後改用 `npm run force-update`，不手打。
  3. `minBuild` 可以和修正同一批推送（建議，兩者一起生效或一起失敗），也可以在修正上線後單獨推送。單獨推送照樣跑 `npm run bump-version`。
  4. 推送後讀回 `https://toosterx.com/runtime-config.json`，確認 `minBuild` 是剛寫的值。
  5. 開一個全新分頁載入首頁，載入完成後 `sessionStorage` 不得出現 `fcb:min-build-reload`（出現代表線上這版自己也低於門檻，立刻照 R-UPD-015 回退）。
  6. 用一個部署前就開著的舊分頁重新整理，確認拿到新版號。
  7. 把值、時間、兩項確認結果記入 evidence。
- **R-UPD-014**：硬條件：`minBuild` 不得大於「含這個值的那次部署」的建置編號。建置編號是打包當下的台北時間，所以值只能是現在或過去，**不得填未來時間、不得多打或少打位數**；測試必須擋下大於執行當下時間的值。若部署平台設了 `FCB_BUILD_ID` 環境變數，建置編號不再是時間，L1 停用並回報顧問。
- **R-UPD-015**：回退：把 `minBuild` 改回上一個值（沒有就 `0`）再推一次。`minBuild` 只升不降是常態；降回只用在填錯。
- **R-UPD-016**：後端不相容變更（R-UPD-010 第 3 項）的順序固定為：新前端先上線 → L1 生效並讀回 → 才部署後端。後端先上是違規。

## 四、L2 停用離線快取

- **R-UPD-020**：只在離線快取本身出問題時用：白畫面、卡在舊版換不掉、新版安裝一直失敗、L1 推了仍有人停在舊版。效果是所有人改走網路、較慢但一定拿到最新版。
- **R-UPD-021**：做法：`swEnabled` 改 `false` 推送 → 讀回線上檔 → 找到原因修好並在 staging 驗證後才改回 `true`。改回 `true` 同樣要顧問裁定。
- **R-UPD-022**：正式站白畫面且 15 分鐘內聯絡不到顧問時，PM 可以先做 L2 再補報（顧問 2026-11-10 預先裁定：L2 只會讓網站變慢，不會壞資料，回退是改回 `true`）。L1 沒有這個例外。

## 五、不得弄壞救援路徑

- **R-UPD-030**：後端變更一律先相容上一版前端；相容做不到才用 R-UPD-016。理由：L0 之下舊版前端可能留在使用者手機上很多天。
- **R-UPD-031**：`/runtime-config.json` 必須維持不快取（`no-store`）且不進離線快取清單；`/sw.js` 維持 `no-cache`。改 `_headers` 或 `globIgnores` 時逐項確認。
- **R-UPD-032**：`minBuild` 與重新載入的保護不得拿掉：每個 `minBuild` 值每個分頁只重新載入一次；送出中（`data-submitting`）不重新載入；彈窗開著或表單編輯中改跳提示。
- **R-UPD-033**：版號（`APP_VERSION`）不得出現在會被長快取的 JS 檔內容裡。只改版號重新打包，`assets/` 的檔名必須完全不變（UPD-1 上線後由測試強制；上線前新增程式碼不得再擴大匯入 `src/version.ts` 的範圍）。
- **R-UPD-034**：本機快照（`localStorage` 的 `fcb:*` 快照）只認資料格式版本 `v`，不認版號。改了快照欄位或語意必須加 `v`，舊快照自動作廢。快照不得用來顯示活動狀態、名額、報名狀態這類會過期的判斷。

## 六、UPD-3（背景下載＋更新提示）上線後才生效

> 這一節在 UPD-3 上線前不適用；上線那一批把本行改成「已生效（版號）」。

- **R-UPD-035**：L0 的行為固定為：開頁用本機已存的版本 → 新版在背景下載完成後才跳提示 →「現在更新」立即換版並重新載入一次 →「稍後」本次不再提示、下次重新開啟自動是新版 → 新版下載完成超過 24 小時，頁面回到前景且畫面安全時自動套用。
- **R-UPD-036**：救援不得依賴主程式能執行：離線快取程式自己要讀 `runtime-config.json`；`index.html` 要有獨立的開機檢查（主程式逾時未掛載就換新版或清掉離線快取後從網路重載，每個分頁一次）。這兩項任一失效不得上線。
- **R-UPD-037**：L1 在這個模式下的流程：向伺服器要新版 → 安裝完成 → 切換 → 重新載入；20 秒內辦不到就清掉離線快取從網路重載。提示框不提供「稍後」。
- **R-UPD-038**：頁面回到前景時重讀 `runtime-config.json`（間隔至少 10 分鐘），不只在載入時讀。
- **R-UPD-039**：離線快取只接管 App 頁面；`/blog`、`/seo`、`/privacy`、`/terms`、`manual.html` 等內容頁不得被換成 App 外殼。
- **R-UPD-041**：動到更新流程（`vite.config.ts` 的 workbox 設定、`sw-control.ts`、`reload-safety.ts`、`chunk-reload.ts`）的卡一律高風險：Opus 設計與終審、staging 先跑至少一天、做一次「壞版救得回來」演練、單獨上線不夾其他卡、上正式前把 staging 證據送顧問。

## 七、上線節奏

- **R-UPD-040**：一般改動集中上線，正式站每天最多兩批（建議中午前一批、晚上一批）。符合 R-UPD-010 的修正與正式站故障修正不受限。理由：每上線一次，所有使用者下次開啟都要重新下載有變動的檔案。
- **R-UPD-042**：上線批次的做後量測要包含「改版後第一次開」：先用上一版開過頁，部署新版後再開同一頁，記 JS 請求數、下載量、內容出現時間。
